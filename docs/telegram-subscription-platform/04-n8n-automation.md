# 04 — Слой автоматизации на вашем n8n

## 1. Принцип разделения

**В ядре (код):** всё, что трогает деньги и доступы — платёжные вебхуки, статусная машина, approve/kick, биллинг. Причины: транзакции, идемпотентность, тесты.

**В n8n:** событийная периферия — уведомления, dunning-цепочки, отчёты, алерты, интеграции. Ошибка здесь не теряет деньги и чинится перезапуском.

Интеграция двумя каналами:

```
Core API ──outbox──► POST https://<ваш-n8n>/webhook/platform-events   (события)
n8n ──────REST────► https://api.platform.tld/v1/... (Bearer service token, готовые действия:
                     send_message, extend_subscription, get_stats)
```

Формат события: `{ "topic": "subscription.grace", "client_id": "...", "payload": {...}, "event_id": 123 }`.
n8n отвечает 200 → outbox помечает `delivered`; иначе ретрай с backoff. Внутри n8n первый узел — Switch по `topic` → под-workflow (паттерн вам знаком по `Heartbeat: Agent Worker v2`).

Важно: n8n **не отправляет сообщения напрямую через токены клиентских ботов** — он вызывает `POST /v1/messages` ядра, которое кладёт сообщение в очередь с rate-limit нужного бота. Токены не покидают ядро.

## 2. Каталог workflow (рекомендуемый набор)

### Для подписчиков (от имени бота клиента, через API ядра)

| Workflow | Триггер | Логика |
|---|---|---|
| **Dunning: напоминания о продлении** | событие `subscription.expiring` (T-3, T-1, T-0 генерирует ядро) | Шаблон сообщения клиента (из настроек) + кнопка оплаты; Wait-ноды не нужны — тайминг даёт ядро |
| **Grace/Win-back цепочка** | `subscription.grace`, `subscription.expired` | T+1: «доступ приостановлен», T+3: оффер с промокодом (создаётся через API), T+14: последнее касание |
| **Welcome-цепочка** | `subscription.activated` | Приветствие, правила клуба, ссылки на все каналы тарифа |
| **Опрос при отмене** | `subscription.cancelled` | Вопрос «почему уходите» с кнопками → ответ в БД → в отчёт клиенту |

### Для клиентов платформы

| Workflow | Триггер | Логика |
|---|---|---|
| **Ежедневный отчёт клиенту** | Cron 09:00 | `GET /v1/stats/daily` per client → сообщение в ЛС клиенту: новые/продлившиеся/отвалившиеся, выручка |
| **Онбординг-дожим** | `client.registered` + не завершил мастер за 24ч | Письмо (ваш SMTP `beget` уже подключён) + сообщение в TG |
| **Биллинг-напоминания** | `platform_invoice.overdue` | Напоминание об оплате абонплаты, предупреждение о suspend |

### Для вас (эксплуатация)

| Workflow | Триггер | Логика |
|---|---|---|
| **Алерты платформы** | `bot.unhealthy`, `payment.webhook_failed`, `reconciliation.mismatch` | В ваш существующий `shmb_n8n_error_bot`; критичное — с упоминанием |
| **Сводка платформы** | Cron 10:00 | MRR, новые клиенты, health всех ботов — вам в ЛС |
| **Бэкап-контроль** | Cron ночью | Проверка pg_dump артефакта, алерт при сбое (по образцу вашего `Daily Lab Recon`) |
| **Синк в таблицы** | Cron / по требованию | Выгрузка платежей в Google Sheets (кред уже есть) для бухгалтерии |

## 3. Что уже есть в вашем n8n и переиспользуется

| Актив | Применение |
|---|---|
| Креды Telegram-ботов (`AP_PRO_chats_bot`, `@uto_appro_bot`, …) | Один из них можно сделать «ботом платформы» для MVP и алертов |
| `shmb_n8n_error_bot` | Готовый канал алертов |
| Postgres-креды (`Postgres all`, `PG_delritm`) | Прямые read-only запросы для отчётов (писать в БД платформы из n8n — нельзя, только через API) |
| SMTP `beget` | E-mail онбординг и счета |
| Google Sheets/Drive creds | Выгрузки для бухгалтерии |
| Паттерны harness (`Message Janitor`, advisory locks, идемпотентность) | Те же приёмы в event-consumer workflow |

## 4. Anti-patterns — чего в n8n не делать

1. **Не обрабатывать платёжные вебхуки в n8n** — потеря/дубль execution = потерянные деньги. Вебхук шлюза → только ядро.
2. **Не кикать/аппрувить из n8n напрямую** — гонки с ядром и двойной rate-limit budget.
3. **Не хранить токены клиентских ботов в n8n credentials** — они принадлежат ядру.
4. **Не строить в n8n статусную машину подписок** (Wait-ноды на дни) — состояние живёт в БД ядра, n8n получает готовые события с таймингом.

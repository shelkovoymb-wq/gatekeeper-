# TG Club Platform — платформа управления закрытыми Telegram-каналами

> B2B2C SaaS: клиенты (владельцы каналов) регистрируются на платформе, подключают своих ботов,
> создают закрытые каналы, настраивают тарифы и платежи для своей аудитории.
> Платформа автоматически контролирует доступ подписчиков по оплаченному периоду.
> Владелец платформы управляет собственными (платформенными) тарифными планами для клиентов.

## Роли в системе

```
Владелец платформы (вы)
   │  управляет платформенными тарифами, комиссиями, клиентами
   ▼
Клиент (владелец канала / автор)
   │  подключает бота и канал, создаёт свои тарифы, принимает оплату
   ▼
Подписчик (конечный пользователь)
      платит клиенту, получает доступ в закрытый канал на оплаченный период
```

## Ключевые архитектурные решения (кратко)

1. **Модульный монолит** (NestJS + TypeScript), а не микросервисы — на старте один деплой, чёткие границы модулей внутри.
2. **Доступ в каналы через join requests**: приватный канал + invite-ссылка с `creates_join_request`, бот аппрувит вход по статусу подписки. Отзыв — `banChatMember` + `unbanChatMember` (kick).
3. **Bot-per-client**: клиент может подключить своего бота (BotFather-токен) — white-label; либо использовать общего бота платформы. Один бэкенд обслуживает N ботов через webhook `/tg/webhook/:botId`.
4. **Платёжная абстракция**: Telegram Stars (нативные подписки), Telegram Payments (ЮKassa и др. провайдеры), внешние шлюзы (ЮKassa напрямую, CloudPayments, CryptoBot/TON) — за единым интерфейсом `PaymentProvider`.
5. **Два уровня тарифов**: платформенные (клиент → вам, лимиты и комиссия) и клиентские (подписчик → клиенту, доступ в каналы).
6. **Access-control как статусная машина** с идемпотентными фоновыми джобами (BullMQ): trial → active → grace → expired → kicked.
7. **Критичное ядро (платежи, доступы) — в коде; вся периферия (напоминания, отчёты, рассылки, алерты, интеграции) — в n8n** через событийную шину (outbox → webhook).

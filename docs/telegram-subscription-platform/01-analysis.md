# 01 — Глубокий анализ и лучшие практики

## 1. Что мы строим

Платформа класса **membership management for Telegram** (аналоги: Tribute, InviteMember, Boosty-подписки, LavaTop, Paywall.pw). Отличие от них: это **ваша** платформа — вы контролируете комиссии, тарифы, white-label ботов и автоматизацию, а клиенты получают кабинет «под ключ».

Бизнес-модель — B2B2C:

- **Доход платформы**: абонентская плата по платформенным тарифам и/или % комиссия с платежей подписчиков.
- **Доход клиента**: продажа подписок на свои закрытые каналы/чаты.

## 2. Анализ конкурентов и выводы

| Платформа | Модель | Что берём как best practice |
|---|---|---|
| **Tribute** | Общий бот, комиссия с платежей, карта любой страны | Оплата «кнопкой» без выхода из Telegram; автопродление; автовыдача и автоотзыв доступа; напоминания о продлении |
| **InviteMember** | Свой бот клиента (white-label), абонплата | Bot-per-client: клиент подключает токен своего бота, бренд клиента, аудитория принадлежит клиенту |
| **Telegram Stars (нативно)** | Встроенные подписки Telegram | Подписки на канал за Stars с периодом 30 дней, автосписание на стороне Telegram, минимум интеграции |
| **Boosty / Patreon** | Уровни (tiers) доступа | Несколько тарифов с разным набором каналов/бонусов; grace period перед отключением |
| **LavaTop / Paywall.pw** | РФ-платежи + зарубежные | Мультипровайдерность платежей: одна витрина, разные шлюзы по гео/валюте |

**Выводы:**

1. Побеждает гибрид: **и общий бот платформы (быстрый старт клиента), и возможность подключить своего** (white-label, аудитория и `/start`-трафик остаются у клиента).
2. **Платёжная мультипровайдерность обязательна**: РФ-карты (ЮKassa/CloudPayments), Telegram Stars (работает везде, включая iOS-аудиторию без карты), крипто (CryptoBot, TON) — у каждого клиента свой набор.
3. **Автоматизация продлений — главная ценность продукта**: напоминания до истечения, grace period, дожим (dunning), win-back после отвала. Это напрямую влияет на удержание выручки клиента (в индустрии dunning возвращает 15–30 % отваливающихся оплат).
4. Ручные операции должны существовать: выдать доступ вручную, продлить в подарок, забанить — без этого поддержка клиентов невозможна.

## 3. Ключевые технические решения (глубокий разбор)

### 3.1 Контроль доступа в канал: join requests — единственный надёжный паттерн

Возможные механики и их сравнение:

| Механика | Как работает | Проблемы |
|---|---|---|
| Публичная ссылка | Одна invite-ссылка на всех | Ссылка утекает — платит один, входят все |
| Одноразовые ссылки | `createChatInviteLink(member_limit=1)` на каждого | Ссылку можно переслать до использования; нужно генерировать/отзывать тысячи ссылок; сложно сопоставить кто вошёл |
| **Join requests (выбор)** | Ссылка с `creates_join_request=true`; вход только после `approveChatJoinRequest` от бота | Утечка ссылки безвредна: бот аппрувит только тех, у кого активная подписка. Точное сопоставление user_id ↔ подписка |

**Реализация (Bot API):**

- Бот добавляется в канал администратором с правами *invite users via link* и *ban users*.
- Платформа создаёт ссылку: `createChatInviteLink(chat_id, creates_join_request=true, name="plan:<id>")`.
- На `chat_join_request` бот проверяет подписку в БД: активна → `approveChatJoinRequest`, нет → `declineChatJoinRequest` + сообщение в ЛС с кнопкой оплаты (join request открывает боту право написать пользователю первым — важная особенность).
- Отзыв доступа: `banChatMember(until_date=now+35s)` → мгновенный `unbanChatMember` («мягкий кик»: человек удалён, но сможет вернуться после оплаты).
- Мониторинг: `chat_member` updates — фиксируем фактические входы/выходы (защита от ручного добавления админом мимо платформы).

### 3.2 Платежи: слой абстракции `PaymentProvider`

Требования: рекуррентность, вебхуки, идемпотентность, возвраты, чеки (54-ФЗ для РФ).

| Провайдер | Рекуррент | Особенности |
|---|---|---|
| **Telegram Stars** | Да, нативные подписки, период строго 30 дней | `sendInvoice(currency="XTR")`, подписочные инвойсы; вывод — в TON через Fragment; комиссия скрыта в курсе Stars; идеально для iOS и зарубежной аудитории |
| **Telegram Payments (провайдер ЮKassa и т. п.)** | Ограниченно | Оплата в интерфейсе Telegram, деньги идут напрямую на счёт провайдера клиента; для рекуррента лучше прямой шлюз |
| **ЮKassa напрямую** | Да (автоплатежи по сохранённой карте) | Чеки 54-ФЗ из коробки; вебхуки `payment.succeeded`; главный шлюз для РФ |
| **CloudPayments** | Да | Гибкие рекурренты, тоже РФ |
| **CryptoBot / TON** | Нет (только разовые) | Крипто-аудитория; продление разовыми платежами |

Best practices платёжного контура:

- **Каждый клиент подключает свои ключи шлюза** (деньги подписчиков идут клиенту напрямую, платформа не становится платёжным агрегатором — это снимает огромный пласт юридических рисков). Комиссию платформы берём из абонплаты и/или считаем по статистике для биллинга.
- **Идемпотентность**: каждый вебхук обрабатывается по `provider_payment_id` с `INSERT ... ON CONFLICT DO NOTHING`; продление подписки — идемпотентная операция «продлить до max(now, paid_until) + period».
- **Outbox-паттерн**: изменение подписки и постановка событий (уведомить, впустить, кикнуть) — в одной транзакции БД.
- Платёж и выдача доступа — **разные шаги**: оплата фиксируется всегда, даже если Telegram API временно недоступен; доступ доводится фоновым воркером до консистентности (reconciliation).

### 3.3 Bot-per-client (white-label)

- Клиент создаёт бота у BotFather, вставляет токен в кабинет.
- Платформа валидирует токен (`getMe`), шифрует его (AES-GCM / libsodium sealed box, ключ вне БД), ставит webhook `https://api.platform.tld/tg/webhook/<bot_id>` c `secret_token` (проверяем заголовок `X-Telegram-Bot-Api-Secret-Token`).
- Один бэкенд обслуживает все боты: по `bot_id` из URL достаём токен и tenant-контекст. Библиотека grammY поддерживает мульти-инстанс из коробки.
- Rate limits Telegram — **на токен** (≈30 msg/s, 1 msg/s в один чат, ~20 msg/min в группу), поэтому очередь исходящих сообщений шардируется по боту.

### 3.4 Два уровня тарифов

**Платформенные тарифы** (управляете вы, полностью настраиваемые):
- параметры-лимиты: число ботов, каналов, подписчиков, сотрудников; комиссия %; фичи-флаги (white-label, API, свои платёжные ключи, приоритетная поддержка);
- реализация: таблица `platform_plans` + JSONB `limits`/`features` — новые лимиты добавляются без миграций; enforcement — guard в API («создать 4-й канал» → 403 при лимите 3).

**Клиентские тарифы** (создаёт клиент для своих подписчиков):
- цена, валюта, период (7/30/90/365 дней или навсегда), trial, набор каналов (один тариф может открывать несколько каналов), промокоды, целевые офферы.

### 3.5 Жизненный цикл подписки (ядро продукта)

```
            оплата            оплата/автосписание
  trial ───────────► active ◄──────────────────┐
    │                  │ paid_until истёк      │
    │ не оплатил       ▼                       │
    └────────►      grace (N дней, настраивается клиентом)
                       │ не продлил            │
                       ▼                       │
                    expired ── kick из каналов │
                       │                       │
                       ▼        оплатил        │
                    churned ───────────────────┘  (win-back)
```

Инварианты:
- Джоба-«жнец» каждые 5 минут: `WHERE status='active' AND paid_until < now()` → grace; `WHERE status='grace' AND grace_until < now()` → expired + событие `access.revoke`.
- Кик и аппрув — идемпотентные команды в очереди с retry/backoff (Telegram может отдавать 429/5xx).
- Любое изменение статуса пишется в `subscription_events` (аудит + аналитика churn).

### 3.6 Мультитенантность

- Single database, shared schema: `client_id` (tenant) во всех клиентских таблицах + составные индексы `(client_id, ...)`.
- На уровне API — tenant-scoping в каждом запросе (guard в NestJS); PostgreSQL RLS как второй рубеж (опционально, включить несложно).
- Данные подписчика глобальны по `tg_user_id`, membership — per-tenant (один человек может быть подписчиком разных клиентов).

## 4. Риски и их закрытие

| Риск | Закрытие |
|---|---|
| Бота удалили из админов канала / отобрали права | Ежечасный health-check `getChatMember(bot)`; алерт клиенту и вам через n8n; статус канала → `degraded` |
| Утечка/компрометация токена бота | Токены шифруются, в логи не пишутся; кнопка «перевыпустить токен» в кабинете; webhook secret |
| Двойная обработка платёжного вебхука | Идемпотентность по `provider_payment_id`, unique constraint |
| Telegram API недоступен во время кика/аппрува | Очередь с retry, reconciliation-джоба сверяет фактических участников (`chat_member` события) со списком активных подписок |
| Админ канала руками добавил «зайца» | `chat_member` update фиксирует вход без подписки → событие `unauthorized_join` → политика клиента: кикнуть или пометить |
| Блокировка бота пользователем | `403 Forbidden: bot was blocked` → флаг `is_reachable=false`, уведомления через канал/e-mail |
| 54-ФЗ / налоги клиента | Платежи идут по ключам клиента → чеки формирует его шлюз; платформа не касается денег подписчиков |
| Рост нагрузки | Ядро stateless, очереди в Redis; PostgreSQL 16 хватит до сотен тысяч подписчиков; дальше — реплики чтения |

## 5. Почему ядро не строим целиком на n8n

n8n отлично подходит для интеграций и периферии (см. [04-n8n-automation.md](./04-n8n-automation.md)), но платёжное ядро и access-control требуют: транзакций БД + outbox, идемпотентных консюмеров с ретраями, юнит-тестов на статусную машину, миграций схемы, ревью кода. Опыт вашего же harness (lock-механизмы, janitor-воркфлоу для зависших задач) показывает, что оркестрация сложной логики в n8n быстро упирается в отладку. Поэтому: **ядро — компактный типизированный сервис, n8n — событийная периферия**, где он силён и где ошибка не стоит денег.

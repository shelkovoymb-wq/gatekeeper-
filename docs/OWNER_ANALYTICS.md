# Детальная статистика платформы

Кто из клиентов сколько заработал, какие каналы это принесли и кто конкретно
кому заплатил — в одном отчёте с графиками и выгрузкой в Excel.

## Где смотреть в интерфейсе

Кабинет владельца → **«Детальная статистика»** (`/owner/analytics`). Ссылка
также стоит кнопкой на странице **«Платформа»** (`/owner/overview`).

На странице:

- **фильтр периода** — быстрые кнопки (7 дней / 30 / 90 / год / всё время),
  произвольные даты, детализация (авто / день / неделя / месяц) и фильтр
  по конкретному клиенту;
- **показатели** — оборот клиентов, комиссия платформы, остаток клиентам,
  средний чек, а также выставлено/оплачено/долг по счетам платформы;
- **графики** — динамика оборота (столбец = оборот периода, нижний сегмент —
  комиссия платформы, верхний — то, что остаётся клиенту), количество платежей,
  доли платёжных провайдеров, топ клиентов и топ каналов по обороту;
- **таблицы** с сортировкой и поиском: «Клиенты», «Каналы», «Кто кому заплатил»,
  «Расчёты с платформой»;
- **«Как считаются цифры»** — методика расчёта прямо на странице; те же
  формулировки уезжают в выгрузку.

Клик по клиенту в блоке «Топ клиентов» фильтрует весь отчёт по нему.

## Выгрузка в XLS

- **«Экспорт всего отчёта в XLS»** — книга из семи листов: Сводка, Динамика,
  Клиенты, Каналы, Платежи, Провайдеры, Расчёты с платформой.
- **«Выгрузить эту таблицу»** — активная вкладка с учётом поиска и фильтров
  плюс лист провайдеров.

Файл формируется в браузере в формате SpreadsheetML 2003 (`.xls`) — открывается
Excel, LibreOffice, Numbers и Google Sheets. Суммы и даты уезжают числами и
датами, а не текстом, поэтому в Excel по ним сразу работают формулы и сводные
таблицы. Внешних библиотек для этого не подключали (`apps/web/src/lib/xls.ts`).

Имя файла транслитерируется в латиницу: Chromium молча игнорирует атрибут
`download` с не-ASCII именем и сохраняет файл как `download` без расширения.

## Как считается каждая цифра

| Показатель | Правило |
|---|---|
| Оборот | Сумма платежей подписчиков в статусе `succeeded` за период |
| Комиссия платформы | Оборот клиента × `commission_pct` его тарифа платформы |
| Остаётся клиенту | Оборот минус комиссия |
| Средний чек | Оборот ÷ количество успешных платежей |
| Оборот канала | Платёж по тарифу делится **поровну** между каналами тарифа — сумма долей по всем каналам равна обороту |
| Оборот тарифов канала (gross) | Те же платежи целиком. По каналам одного тарифа пересекается, складывать нельзя |
| Расчёты с платформой | Счета `platform_invoices`, чей период пересекается с выбранным диапазоном |

Комиссия считается по **текущей** ставке тарифа клиента, а не по той, что
действовала в момент платежа: исторических ставок схема не хранит.

## API

```
GET /v1/platform/analytics?from=2026-08-01&to=2026-08-16&granularity=day&clientId=<uuid>&limit=5000
```

Только для владельца платформы (`role=owner`, `client_id = null`) — тот же
`assertOwner`, что и на остальных ручках `/v1/platform/*`.

Параметры:

| Параметр | Значение |
|---|---|
| `from`, `to` | Границы включительно, `YYYY-MM-DD`. По умолчанию — последние 30 дней. Мусор игнорируется, перевёрнутый период разворачивается |
| `granularity` | `day` \| `week` \| `month`. По умолчанию подбирается по длине периода; слишком дробная огрубляется, чтобы график не разъезжался |
| `clientId` | UUID клиента; значение не-UUID игнорируется |
| `limit` | Размер реестра платежей, по умолчанию 500, максимум 20 000 |

В ответе: `period`, `filters`, `totals`, `trend`, `clients`, `channels`,
`providers`, `ledger`, `settlements` и `methodology` (тексты правил расчёта —
интерфейс и выгрузка берут их отсюда, чтобы формулировки не разъезжались).

Веб-кабинет ходит на бэкенд через свой прокси-роут
`apps/web/src/app/api/platform/analytics/route.ts` — JWT лежит в httpOnly-cookie
и в браузер не отдаётся.

## Проверка

- Юнит-тесты: `pnpm --filter @gatekeeper/api test` (период, корзины, сборка
  отчёта) и `pnpm --filter @gatekeeper/web test` (генератор XLS, листы отчёта).
- Живой Postgres: `DATABASE_URL=postgres://… ALLOW_TRUNCATE=1 npx tsx scripts/analytics-smoke.ts`
  из `apps/api` — сеет пару клиентов с каналами и платежами и проверяет, что SQL
  считает ожидаемые суммы (в том числе что сумма долей каналов равна обороту).
  **Скрипт делает `TRUNCATE` рабочих таблиц — гонять только на тестовой базе.**
